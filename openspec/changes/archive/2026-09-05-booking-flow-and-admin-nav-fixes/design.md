## Context

See proposal.md - Why. Six independent defects, grouped here by the code they touch. Key existing mechanics this design builds on rather than replaces:

- Slot holds are keyed by an `fg_session_id` cookie (`lib/session.ts`), not by auth user, and already survive the login redirect — `/api/slots/status` already reports a held slot back as `status: 'selected'`. The gap is purely client-side state hydration in `components/BookingSystem.tsx`.
- The OTP-verified login channel is already captured as a signed `fg_auth_channel` cookie (`lib/session.ts`'s `readAuthChannel()`) and already used to lock one field at checkout (`components/CheckoutForm.tsx`'s `lockedField` prop). Extending it to the profile page is a second consumer of the same signal, not a new mechanism.
- Slot blocking already has a full model (`AdminSlotBlock`), UI (`components/SlotManagementClient.tsx`), API (`app/api/fg-admin/platform/slots/route.ts`), and approval workflow (`lib/admin.ts`, `app/fg-admin/platform/approvals/`) for `super_admin`/`arena_admin`. The gap for managers is a role-allowlist omission plus the lack of a date-range dimension, not a missing feature.
- `role` and `userId` are already resolved server-side once per request in `app/layout.tsx` and passed into `Header` as props — no new session plumbing is needed to make the header role-aware.

## Goals / Non-Goals

**Goals:**
- Close each of the six defects with the smallest change that reuses existing mechanics (session cookie, approval workflow, checkout's field-lock pattern).
- Make the admin header role-based so it doesn't regress every time a staff member is one click away from a non-`/fg-admin` page.
- Let managers cover ground-unusable dates in one submission (a day or a range of days), including beyond the 15-day booking window.

**Non-Goals:**
- Not building a general recurring/day-of-week block schedule (e.g. "block every Monday") — only an explicit date range.
- Not changing the underlying `AdminSlotBlock`/`ArenaHoliday` schema to add native range columns — a submitted range is expanded into individual per-date (and per-hour) rows client/server-side, matching the existing pattern already used to expand an hour-range into per-hour rows.
- Not reworking the approval workflow itself (who approves, notification channels) — only extending its existing payload shape to carry a list of dates instead of one.
- Not rebuilding `ProfileMenu`/dashboard sidebars from scratch — only removing entries that now exactly duplicate a Header nav destination.

## Decisions

**1. Hydrate `selectedSlots` from `/api/slots/status`, don't change the login redirect.** `fetchWindow` in `BookingSystem.tsx` currently only *removes* slots from local state that the server no longer reports as available/selected. Changing it to also *add back* any `status: 'selected'` slot not yet in local state fixes the bug on every fetch (initial load, 30s poll, tab refocus) — not just the login-redirect case — and needs no change to what `next` carries, since `date` is already preserved there and the slot hold itself is what carries the actual selection.
  - Alternative considered: pass the selected slot list through the `next` query param and parse it back on mount. Rejected — it duplicates information the server already has authoritatively (the lock), and wouldn't fix the same staleness on a plain page refresh or the 30s poll.

**2. Reuse checkout's `lockedField` pattern for the profile page verbatim.** Read `readAuthChannel()` server-side (the profile page's data currently comes from a client-side `fetch('/api/dashboard/profile')`; the channel will be threaded through that same response rather than adding a second endpoint) and pass `lockedField` down to render the matching input `readOnly` with the existing "(verified)" badge/lock icon treatment. The `PUT` handler gains a matching server-side check: if the payload's value for the locked field differs from the stored value, reject with 400.
  - A session predating this change has no `fg_auth_channel` cookie set — `readAuthChannel()` already returns `null` for that case (documented in the earlier change that introduced it), which correctly falls back to "nothing locked" rather than erroring.

**3. Header becomes role-based, not path-based; the only role check that matters is whether `role` is a staff role.** Replace `isAdminPath = pathname.startsWith('/fg-admin')` with a check against the known staff roles. This is the specific approach the user confirmed (over a narrower per-page back-link fix). Add the missing `arena_admin` branch to the nav array while here, since a role rendering an empty nav is the same class of bug. The admin header currently has no mobile drawer (unlike the customer header) — since it will now render on more pages/viewports, add a minimal one reusing the same disclosure pattern as the customer header's drawer.
  - Risk: showing the "ADMIN" branded header on a page primarily designed for the customer flow (e.g. staff viewing `/arena/[slug]` themselves) could look inconsistent. Accepted per user's explicit choice — staff always having their nav available outweighs the cosmetic mismatch on the few pages they'd visit as a "customer" themselves.

**4. Booking QR/ticket page picks its bottom actions by role, computed server-side.** `app/booking/success/[ref]/page.tsx` is already a server component with DB access; add a `readAuthRole()` call. For a staff role, replace "BOOK AGAIN" (points at the customer purchase flow, meaningless for staff looking at someone else's booking) with a link to that role's own bookings list (`/fg-admin/arena/bookings` for manager, `/fg-admin/platform/bookings` for super_admin/arena_admin), and drop "MY BOOKINGS" → `/dashboard` since that's the customer dashboard, not theirs. Customers keep the existing two buttons unchanged.

**5. Manager slot blocking: fix the allowlist, add a real manager-facing block UI, and expand a date range server-side.**
  - `MANAGER_ALLOWED_ACTIONS` gains `block_add`/`block_delete`, routing manager submissions through the same approval-request path `holiday_add`/`holiday_delete` already use for manager — no new workflow, just extending the existing list.
  - Correction found during implementation: `SlotManagementClient.tsx` (at `/fg-admin/platform/slots`) is not actually what a manager uses day to day — the manager's "Slots" nav link goes to `/fg-admin/arena/slots` (`ArenaSlotClient.tsx`), a deliberately narrower page that only renders the actions a manager may perform (entry mode, holidays via `ManagerHolidayClient.tsx`) — `SlotManagementClient.tsx` also renders pricing/slot-structure controls managers aren't allowed to use. So the block-request UI is added as a new `components/ManagerBlockClient.tsx`, following the exact same pattern as `ManagerHolidayClient.tsx` (own fetch of `/api/fg-admin/platform/slots`, same POST contract), wired into `ArenaSlotClient.tsx` next to Holidays. `SlotManagementClient.tsx`'s existing block form (used by `super_admin`/`arena_admin`, who do reach it via the Header nav) separately gains the same date-range capability.
  - Both forms gain a "Start Date"/"End Date" pair (End Date optional, defaults to Start Date) and keep the existing From/To hour range. Rather than looping client-side per date/hour combination (which would file one API call, and for a manager one separate approval request, per combination), the client sends a single request with `booking_date`, `end_date`, `from_hour`, `to_hour`; the server expands both the date range and the hour range into individual `admin_slot_blocks` rows (direct-apply) or a single approval payload (manager) — one submission, one approval record, regardless of how many day×hour combinations it covers.
  - The `BLOCK_SLOT_REQUEST` approval payload changes from `{ bookingDate, slots: [timeSlot], reason }` to `{ dates: string[], slots: string[], reason }`. Update the three call sites that assumed a single `bookingDate`: `PayloadSummary` in `app/fg-admin/platform/approvals/page.tsx`, `summarizeApprovalPayload` in `lib/admin.ts` (the approval-email one-liner), and the approval-decision handler in `lib/admin.ts` that inserts `admin_slot_blocks` rows on approval (gains a nested loop over dates × slots). Also add a `BLOCK_SLOT_REQUEST` badge/detail case to `ArenaSlotClient.tsx`'s own request-history renderer, so a manager sees their block requests listed the same way holiday requests already are.
  - Dropped from scope: extending the Holiday (full-day closure) form to a date range. The user's request ("a particular day, or a particular slot from a range of days") maps to the block form's range handling; a manager closing several individual days can still submit the existing single-date holiday form once per day, unchanged from today.
  - No max-date validation is added anywhere in this path — confirmed today's `block_add`/`holiday_add` handlers and `/api/slots/status` already handle a beyond-window block/holiday correctly (the status endpoint just doesn't need to query it until the date is inside the window), so "beyond 15 days" requires no new window-bypassing logic, only making the date field itself unrestricted (it already is).

**6. Nav de-duplication: Header nav is the source of truth; trim `ProfileMenu` and page-local dashboard links against it.** For each staff role, `ProfileMenu`'s role branch drops any link whose destination is already in that role's Header nav entries (kept per the user's chosen approach), leaving Logout and "Signed in as" for every role, and leaving the `customer`/`player` branch untouched (nothing to de-duplicate against, since the customer header doesn't surface those links elsewhere). Page-local dashboard sidebars (`SuperAdminDashboardClient.tsx`) and card grids (`app/fg-admin/arena/dashboard/page.tsx`, `app/fg-admin/platform/dashboard/page.tsx`) drop links that are pure duplicates of a Header nav destination for that role, while keeping any dashboard content that isn't just a nav link (stats, in-page tab panels).

## Risks / Trade-offs

- [Risk] Reconciling `selectedSlots` from server state on every poll could fight a user's own in-flight click if a lock/unlock request is still in transit when a poll lands. → `toggleSlotForDate` already updates local state optimistically right after a successful lock/unlock call; the poll-driven reconciliation only adds/removes based on the latest server snapshot, so a slot the user just locked will already show as `'selected'` server-side by the time the next poll runs (well within the 30s interval), and a slot they just unlocked is already removed from local state before any poll could re-add it.
- [Risk] Expanding a date range × hourly range client-side into many individual `POST` calls (as the hour-range expansion already does) could be slow or partially fail for a large range. → Match the existing hour-expansion error handling (report which calls failed, let the manager retry just those); not introducing a new failure mode, just extending the existing one along a second axis. A sane upper bound (e.g. reject a range over some number of days) can be added in the UI if this proves necessary, but isn't required by the stated use case (maintenance windows, not month-long closures).
- [Risk] Making the admin header role-based means it now renders on pages that never expected an "ADMIN"-branded header before (e.g. `/arena/[slug]` visited by a manager). → Accepted per the user's explicit decision; no page-specific opt-out is being added, since staff still being able to navigate is the point.
- [Risk] The profile page's OTP-channel lock is enforced server-side per this design, but pre-existing staff-role updates to `arena_admins`/`security_staff` cascades in the same `PUT` handler are unaffected — this change only adds a rejection when the *locked* field's value is changing, not a new field or code path.
