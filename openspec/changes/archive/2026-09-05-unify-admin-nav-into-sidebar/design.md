## Context

See proposal.md - Why. Key facts from investigation (all confirmed this session, not assumed):

- No `app/fg-admin/**/layout.tsx` exists anywhere today — every admin page is a standalone route relying only on the root `app/layout.tsx`'s global `<Header/>`. A persistent sidebar therefore needs a new shared layout, not a tweak to an existing one.
- `components/Header.tsx` already computes a role-based per-role nav item array (`super_admin`, `arena_admin`, `manager`, `security`, `accountant`) rendered as top-bar links plus a mobile drawer — this is the list to relocate into the new sidebar, not rebuild from scratch.
- `app/fg-admin/platform/super-admin/SuperAdminDashboardClient.tsx` has its own `<aside className="w-64 ...">` with 6 tab buttons (Overview, Arena & Staff, Timings, Block Slots, Approvals, Settings) driving local `activeTab` state (`useState('overview')`, no query-param awareness), plus a short list of `<a>` links below a divider (only "Accountants" remains there after the previous change's dedup pass — everything else was already trimmed as a Header-nav duplicate).
- The dashboard's "Approvals" tab (`activeTab === 'approvals'`, `fetchApprovals`, `handleResolveRequest`, `approvals`/`approvalsLoading` state, and the `formatBlockSlotPayload`/`ApprovalPayloadDetail` helpers added last session) always renders a plain raw-JSON dump for most request types — confirmed via grep that none of that state/those functions are read anywhere else in the file, so removing the tab can remove all of it cleanly.
- The standalone `app/fg-admin/platform/settings/page.tsx`: its "Super Admin Password" form posts to the same `/api/fg-admin/platform/credentials` action already exposed (and working) at `/fg-admin/platform/credentials` — confirmed duplicate. Its read-only settings-value list has a permanently-disabled "UPDATE VALUE" button — dead UI. Its only non-duplicate piece is `<ChangeSuperAdminEmailForm>` (a self-contained `'use client'` component, confirmed via grep to have no other call site) which calls `PUT /api/dashboard/profile` directly with `{name, email, customer_mobile: ''}` — it needs `currentName`/`currentEmail` props, and the dashboard's `SuperAdminSettings` interface/`GET /api/fg-admin/super-admin/settings` response has `email` but no name field today (confirmed via reading the route handler).
- `app/fg-admin/platform/dashboard/page.tsx`'s super_admin-gated "Settings" Quick Action card linking to the doomed page is already dead code — that page redirects super_admin away (`if (context.role === 'super_admin') redirect('/fg-admin/platform/super-admin')`) before the card could ever render for them.

## Goals / Non-Goals

**Goals:**
- Exactly one left-hand navigational surface per admin page, for every staff role.
- No loss of any currently-working capability (email change, password change, settings edits, arena management, etc.) — only removal of genuinely dead/duplicate code paths.
- Minimal blast radius: reuse the existing per-role nav data and existing page components; don't restructure how any individual admin page's content works internally beyond what's needed to stop it from rendering a second left column.

**Non-Goals:**
- Not deep-linking every dashboard sub-tab (Arena & Staff, Timings, Block Slots) from the global sidebar — only "Dashboard" (lands on Overview) and "Settings" (deep-links via `?tab=settings`) get sidebar entries; the rest stay reachable only via the page's own horizontal tab bar, since they weren't flagged as needing a global shortcut and are arena-scoped tools nested under that one page.
- Not auditing every other admin page for duplicate content the way Approvals/Settings turned out to be — only those two, since they were the ones actually found and confirmed during this investigation. If more turn up later, that's a separate change.
- Not changing anything about the customer-facing header — this only touches the admin (staff-role) rendering branch of `Header.tsx`.

## Decisions

**1. New `app/fg-admin/layout.tsx` (server component) + new `components/AdminSidebar.tsx` (client component), rather than folding sidebar rendering into the existing root layout or into `Header.tsx` itself.** A layout scoped to `/fg-admin/*` is the natural place for a sidebar that should appear on every admin page and nowhere else; keeping it separate from the root layout means the customer-facing pages are untouched. `AdminSidebar` needs `usePathname()`/`useSearchParams()` for active-state highlighting and its own mobile-drawer toggle state, so it has to be a client component; the layout itself stays a server component that just resolves `role`/`arenaId` once (via `readAuthRole()`/`readArenaId()`, the same helpers `app/layout.tsx` already uses) and either renders `<AdminSidebar/>` + a flex content area, or — for a non-staff role (the `/fg-admin/login` page, or any edge case) — renders `{children}` directly with no sidebar at all.

**2. `Header.tsx`'s admin branch loses its nav array and mobile drawer entirely, keeping only branding + `ProfileMenu`.** The per-role `adminNavItems` arrays currently in `Header.tsx` move as-is into `AdminSidebar.tsx` (same hrefs/labels, just rendered as a vertical list instead of a horizontal one) — no new nav data is invented for arena_admin/manager/security/accountant beyond what already existed in `Header.tsx`, per the earlier consolidation. The admin branch's mobile hamburger/drawer also moves into `AdminSidebar` (it needs to own its own mobile toggle now that it's rendered from a layout rather than from `Header`), so `Header.tsx`'s admin branch shrinks to: logo, and `ProfileMenu` — no `mobileMenuOpen` state needed there for the admin case (the customer-facing branch keeps its own drawer unchanged).

**3. Super admin dashboard's tab strip becomes a horizontal bar, not a second sidebar entry set.** Changing the existing `<aside className="w-64 space-y-1 p-4">...</aside>` to a horizontal flex row (e.g. `flex gap-2 overflow-x-auto` in a bar above the tab content) is a layout-only change — the tab buttons, `activeTab` state, and every tab's content stay as they are except for the two removals below. This avoids inventing query-param-addressable sidebar entries for Overview/Arena & Staff/Timings/Block Slots, which aren't needed per the Non-Goals above.

**4. Remove the in-page Approvals tab entirely; sidebar's Approvals entry points at `/fg-admin/platform/approvals`.** Delete the tab button, the `activeTab === 'approvals'` render block, `fetchApprovals`, `handleResolveRequest`, the `approvals`/`approvalsLoading` state and their `useEffect`, and the now-unused `formatBlockSlotPayload`/`ApprovalPayloadDetail` helpers (added last session specifically to patch this tab's raw-JSON rendering — moot once the tab is gone). The standalone page already has the richer `PayloadSummary` rendering built last session, so nothing is lost.

**5. Delete the standalone Settings page; relocate its one real capability into the dashboard's Settings tab; sidebar's Settings entry deep-links via `?tab=`.**
   - Add `first_name`/`last_name` (or a computed `name`) to `GET /api/fg-admin/super-admin/settings`'s response — `getSuperAdmin()` already returns these fields (used elsewhere, e.g. the profile-update route), the settings route just isn't surfacing them yet.
   - Add the matching field(s) to the client's `SuperAdminSettings` interface and render `<ChangeSuperAdminEmailForm currentName={...} currentEmail={settings.email} />` inside the existing `activeTab === 'settings'` block, alongside the current cutoff/booking-window/refund/GST controls.
   - Read the initial tab from `useSearchParams().get('tab')` (falling back to `'overview'`) instead of a bare `useState('overview')`, so `AdminSidebar`'s Settings entry can link to `/fg-admin/platform/super-admin?tab=settings` and land directly on that tab.
   - Delete `app/fg-admin/platform/settings/page.tsx`. `components/ChangeSuperAdminEmailForm.tsx` stays (now imported from the dashboard client instead).
   - Remove the dead super_admin-gated "Settings" Quick Action card in `app/fg-admin/platform/dashboard/page.tsx` (unreachable already, now also pointing at a deleted route) and update the stale code-comment in `app/fg-admin/platform/audit-logs/page.tsx` that cited the settings page as an example pattern (point it at `app/fg-admin/platform/credentials/page.tsx` instead, which uses the identical auth check).

## Risks / Trade-offs

- [Risk] A brand-new shared layout wrapping every `/fg-admin/*` route is the highest-blast-radius single file in this change — a bug in it (e.g. mis-detecting a non-staff session) could break every admin page at once. → Keep its logic minimal and mirror exactly what `app/layout.tsx` already does today to resolve `role`/`arenaId` (same helpers, same fallback of "not a staff role → render children unchanged"), rather than inventing new session-resolution logic.
- [Risk] Moving the mobile nav drawer out of `Header.tsx` and into `AdminSidebar` changes where that state lives — a staff member mid-session with an old cached page could see an inconsistent mobile menu during a deploy. → Accepted; this is true of any client-side nav refactor and self-corrects on next navigation/reload.
- [Risk] Deep-linking via `?tab=settings` means any other place that already links to `/fg-admin/platform/super-admin` without a query param still lands on Overview, not Settings — that's the existing behavior for those links today, so nothing regresses; only the new sidebar entry needs (and gets) the query param.
- [Risk] Removing the in-page Approvals tab and standalone Settings page are both irreversible-in-place deletions of working (if duplicate) UI. → Mitigated by the explicit user sign-off captured in proposal.md, and by relocating the one non-duplicate capability (email change) before deleting rather than after.
